# 콘텐츠 생성 지연 원인 및 속도 개선 계획 (2026-01-27)

## 한줄 결론
지연의 핵심 원인은 (1) 생성 뒤 리뷰/자동수정까지 직렬로 모두 기다리는 구조, (2) 리뷰/수정 요청이 "파일 전체 내용"을 포함해 매우 커지는 점, (3) 대형 review 객체를 `jobs.json`에 동기식으로 반복 저장하는 점입니다.

## 코드 근거로 본 병목 후보
1. 직렬 파이프라인 + 리뷰/자동수정 루프
- 생성 완료 후 리뷰와 자동수정 루프를 같은 요청 흐름에서 연속 수행합니다.
- 자동수정은 `review -> fix -> review`를 최대 3회 반복할 수 있습니다.
- 근거: `api/src/content-generator.ts:513`, `api/src/content-generator.ts:523`, `api/src/content-generator.ts:527`

2. 리뷰/수정 프롬프트가 매우 큼 (토큰/지연 증가)
- 리뷰/수정 요청에 `prompt + index.html 전체 + script.js 전체 + style.css 전체`가 포함됩니다.
- 근거: `api/src/llm/review.ts:115`, `api/src/llm/review.ts:130`, `api/src/llm/review.ts:176`, `api/src/llm/review.ts:195`
- 추가 관찰: 시스템 프롬프트 길이가 약 17,695자(약 4,400토큰 추정)입니다. 여기에 파일 전체 내용을 더하면 리뷰/수정 단계가 특히 느려질 가능성이 큽니다.

3. jobs.json 동기식 전체 쓰기 + 대형 review 저장
- `updateJob` 호출마다 `jobs.json`을 동기식으로 전체 덮어씁니다.
- 근거: `api/src/job-manager.ts:44`, `api/src/job-manager.ts:53`, `api/src/job-manager.ts:117`, `api/src/job-manager.ts:126`
- 실제 diff에서 `jobs.json`에 review 객체가 크게 붙어 파일이 비대해졌던 흔적이 있습니다. 이 상태에서 동기식 전체 쓰기를 여러 번 하면 체감 지연이 생길 수 있습니다.

## 파싱 실패("Z.ai 응답 JSON 파싱 실패") 해석
- 실패 지점은 `JSON.parse(normalizedPayload)`입니다.
- 근거: `api/src/llm/zai-output.ts:37`
- 가장 가능성 높은 원인: 모델이 JSON 문자열 내부에서 따옴표/개행 이스케이프를 깨뜨린 응답을 내는 경우입니다. HTML/JS/CSS 본문은 따옴표가 많아 이 문제가 자주 발생합니다.

## 속도 개선 전략: 빠른 개선 → 구조 개선 순서

### 0단계: 즉시 가능한 운영 설정 (코드 변경 없이)
목표: 체감 시간을 가장 빠르게 줄이기
1. 리뷰/자동수정 비활성화 또는 축소
- 옵션 A: `LLM_REVIEW_ENABLED=false`
- 옵션 B: `LLM_REVIEW_AUTO_FIX_ENABLED=false`
- 옵션 C: `LLM_REVIEW_AUTO_FIX_MAX_ATTEMPTS=1`

2. 리뷰를 빠른 모델로 분리
- `ZAI_REVIEW_MODEL`을 생성보다 더 빠른 모델로 지정

이 단계는 "품질 vs 속도" 트레이드오프가 있으므로 사용자 확인이 필요합니다.

### 1단계: 계측(측정) 먼저 넣기 (TDD 권장)
목표: 어디서 시간이 오래 걸리는지 수치로 확인

실행 계획 (TDD 순서)
1. 테스트 작성 (실패 확인)
- 생성/리뷰/수정 단계별 시간이 job에 기록되는지 테스트 추가
- 위치: `tests/api-content-timing.test.js` (신규)

2. 최소 구현
- 각 단계 전후로 시간 측정
- 예: `generationMs`, `reviewMs`, `fixMs`, `totalMs`

3. 통과 확인
- `npm test` 실행

4. 활용
- 느린 구간을 실제로 확인한 뒤 2~3단계의 우선순위를 확정

### 2단계: 직렬 대기를 줄이는 구조 개선 (체감 속도 개선 핵심)
목표: "완료"를 더 빨리 반환

권장 방향 (추천)
1. 생성 완료 시점을 "완료"로 간주하고, 리뷰/자동수정은 백그라운드로 분리
- 예: 상태를 다음처럼 분리
  - `completed_pending_review`
  - `review_completed`
  - `review_failed`
- 장점: 사용자 체감 완료 시간 단축
- 단점: 상태 모델 변경 필요

대안 (보수적)
2. 리뷰는 하되 자동수정 루프를 비활성화 또는 1회로 제한

### 3단계: 리뷰/수정 요청 크기 줄이기 (지연/비용 동시 개선)
목표: 토큰 수를 줄여 LLM 응답 시간을 단축

아이디어 (낮은 리스크 순)
1. 리뷰 입력을 축약
- 전체 파일 대신 핵심 섹션만 전달하거나, 파일을 요약해서 전달
- 결정론적 검사에서 통과한 항목은 LLM에 반복 전달하지 않기

2. 리뷰를 2단계로 분할
- 1차: 결정론적 + 간단 규칙 기반 검사
- 2차: 1차에서 실패했을 때만 LLM 리뷰 수행

### 4단계: 파싱 안정성 개선 (실패율/재시도 감소 → 속도 간접 개선)
목표: "잘 생성했는데 파싱 실패"를 줄이기

권장 방향 (추천)
1. 파일 내용을 base64로 요청/응답
- JSON 문자열 이스케이프 문제를 크게 줄일 수 있음
- 파서에서 base64 decode 후 저장

보완책
2. 파싱 실패 시 원문을 디버그 파일로 저장
- 예: `api/data/debug/zai-raw-{jobId}.txt`
- 다음 개선의 근거 확보

### 5단계: job 저장 I/O 개선 (작지만 확실한 개선)
목표: 이벤트 루프 블로킹과 대형 JSON 반복 쓰기 줄이기

아이디어
1. 동기식 → 비동기식으로 전환 + 디바운스 저장
- 여러 `updateJob`을 짧은 시간에 묶어서 1회 저장

2. review는 분리 저장
- `jobs.json`에는 요약만 저장하고, 상세 review는 별도 파일에 저장

## 구현 우선순위 제안 (현실적인 순서)
1. 0단계 운영 설정으로 즉시 체감 시간 단축
2. 1단계 계측 추가로 병목을 수치로 확인
3. 2단계에서 "완료 시점 분리" 또는 "자동수정 축소" 결정
4. 4단계(base64)로 실패율을 낮춰 낭비 시간 제거
5. 3단계/5단계로 비용과 안정성 최적화

## 사용자 확인이 필요한 선택지
1. 리뷰/자동수정의 "필수성" 수준은 어느 정도인가?
2. 생성 완료를 먼저 반환하고 리뷰는 나중에 끝내도 되는가?
3. 속도 개선을 위해 리뷰 품질(엄격도) 일부를 낮춰도 되는가?
